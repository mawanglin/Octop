# 开发流程与编码规范

## 1. 流程

1. **澄清需求**：要做什么、输入输出是什么、在哪里运行、有没有现成代码。有多种理解时列出来让用户选，不要默认挑一种。能用一句话说清"做完的标准"（比如"`pytest` 通过，`POST /orders` 返回 201"）再动手。
2. **先读代码**：改现有项目时，先看 README、目录结构、入口、相关模块和已有测试，沿用项目已有的写法、命名、依赖和目录约定；不清楚的项目先请「代码仓库导读」梳理。
3. **说方案**：改动超过几十行或涉及多个文件时，先用几句话说明改哪些文件、怎么改、怎么验证，用户确认后再写。
4. **小步实现**：一次只做一件事；只改和任务相关的代码，不顺手重构、不改无关格式；不加没被要求的功能和配置项。
5. **写测试**：新功能至少覆盖正常路径和一个错误路径；修 bug 先写一个能复现问题的测试，确认它失败，再修到通过。
6. **自检**：运行 `code-check`，修到没有失败；跳过的项说明原因。
7. **交付**：按第 5 节模板说明改了什么、怎么运行、怎么验证、还有什么限制。

## 2. 常见任务

| 任务 | 做法 |
|------|------|
| 新功能 | 先定接口（函数签名 / API 路径和请求响应），再写实现和测试；入口薄、逻辑集中在可测试的函数里 |
| 修 bug | 复现 → 定位（看报错堆栈、加日志、二分缩小范围）→ 写失败测试 → 最小修复 → 检查同类代码是否有同样问题 |
| 加接口 | 参数校验、错误码（400 参数错、401 未登录、403 无权限、404 不存在、409 冲突、422 校验失败）、分页、鉴权、测试；更新接口文档 |
| 重构 | 先确认有测试覆盖，没有就先补；重构不改行为，和功能改动分开提交 |
| 性能优化 | 先测量找出瓶颈（计时、分析器、数据库执行计划），再优化，优化后再测一次对比 |
| 看不懂的报错 | 读完整堆栈，从最靠近自己代码的那一行看起；搜索报错原文；最小化复现 |

## 3. 编码规范

**通用**：函数短小、只做一件事；命名说明用途（`unpaid_orders` 而不是 `data2`）；不写重复代码，但也不为两三行的相似代码硬抽象；注释写"为什么"，不写"做了什么"；错误要么处理要么向上抛，不吞掉异常。

**Python**：类型注解；`pathlib` 处理路径；`with` 管理文件和连接；读写文件指定 `encoding="utf-8"`；用 `logging` 不用 print 调试；依赖写进 requirements / pyproject 并固定主版本。

**TypeScript / JavaScript**：开启 `strict`；不用 `any`（确实未知用 `unknown` 再收窄）；`const` 优先；异步统一 `async/await` 并处理拒绝；React 组件保持小而纯，副作用放 `useEffect` 并写全依赖。

**SQL**：参数化查询，绝不拼接用户输入；改表结构写迁移脚本；`UPDATE` / `DELETE` 必须带 `WHERE`；复杂查询交给「SQL 数据库专家」看执行计划。

## 4. 安全底线

- 密钥、密码、令牌放环境变量或 `.env`（加入 `.gitignore`），不写进代码和提交记录；提交前可请「代码安全扫描」检查。
- 所有外部输入都要校验；输出到网页要转义；文件路径防止 `../` 越界；不用 `eval` / `exec` / `shell=True` 处理用户输入。
- 密码用 bcrypt / argon2 等成熟库哈希，不自己发明加密。
- 删除数据、改生产配置、执行数据库迁移、`git push --force` 等不可逆操作，先说明影响并得到用户确认。
- 不编写恶意软件、绕过授权、批量爬取违反网站协议或窃取数据的代码。

## 5. 交付说明模板

```
## 改了什么
- 文件 A：……（为什么）
- 文件 B：……

## 怎么运行
命令……

## 验证结果
code_check：语法 / 规范 / 测试 通过；（跳过：mypy，未安装）
手动验证：……

## 注意 / 后续
- 已知限制……
- 建议……（不在本次范围内）
```
