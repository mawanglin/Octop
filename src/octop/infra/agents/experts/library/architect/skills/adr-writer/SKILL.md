# 架构决策记录（ADR）

> `scripts/`、`references/` 路径相对于本技能目录。

ADR 记录一个**重要的、不容易改的**决定：当时面临什么问题、考虑过什么、为什么这样选、付出什么代价。半年后接手的人（包括你自己）靠它理解“为什么是这样”。

## 1. 什么时候写

写：选数据库、消息队列、框架、部署方式；服务拆分或合并；认证方案；对外接口的重大约定；一致性策略；决定**不做**某件常见的事。

不写：命名、格式、局部实现细节，这些放代码注释或规范文档。

判断标准：如果以后有人问“为什么不用 X”，而答案不在代码里，就该写。

## 2. 用脚本管理

```bash
python scripts/adr.py new "订单事件用消息队列异步通知下游" --dir docs/adr --deciders "后端负责人,订单组"
python scripts/adr.py list --dir docs/adr
python scripts/adr.py check --dir docs/adr
python scripts/adr.py status 0003 已采纳 --dir docs/adr
python scripts/adr.py supersede 0003 0007 --dir docs/adr      # 0007 取代 0003
```

- 文件名 `NNNN-标题.md`，编号四位、只增不改、不重用；被废弃的决定改状态，**不删文件**；
- 状态：提议中、已采纳、已弃用、已被取代（也认 proposed / accepted / deprecated / superseded）；
- `new` 生成带占位提示的模板，要把每一节写完；`list` 列出所有 ADR；
- `check` 检查：编号重复或跳号、标题编号和文件名不一致、状态不合法、必填章节缺失或还是模板占位、备选方案不足两个、已采纳的没写“代价和风险”、取代关系两边是否对应、取代的对象是否存在。退出码：0 没有必须处理的，3 有必须处理的，1 输入错误；
- `supersede` 同时修改两份文件：旧的变成“已被取代”并写“被取代：新编号”，新的写“取代：旧编号”。

默认目录是 `docs/adr`，用户有自己的位置就用 `--dir`。

## 3. 各节怎么写

| 节 | 写什么 | 常见错误 |
|----|--------|----------|
| 背景 | 面临的问题、现状和约束、为什么现在必须决定；带数字和事实 | 一上来就写结论；背景写成方案介绍 |
| 决策驱动因素 | 这次决定最看重的 3～5 件事 | 没写，导致对比没有标准 |
| 备选方案 | 至少两个，每个写做法、优点、缺点；**包括“什么都不做”或“保持现状”** | 只有一个方案；其他方案是稻草人，故意写得很差 |
| 决策 | 一句话写清选哪个；再用两三句话说为什么选它、为什么不选其他 | 含糊（“倾向于”）；没写理由 |
| 后果：好处 | 这个决定带来什么 | 只写好处 |
| 后果：代价和风险 | 要付出什么、可能出什么问题、怎么缓解；**不能为空** | 没有代价的决定不存在，写不出来说明没想清楚 |
| 重新评审条件 | 出现什么情况要回头重新决定，尽量可度量 | 没写，决定变成永久的 |

写作要点：用事实和数字，少用形容词；不甩锅给“业界最佳实践”，说明在**我们的**约束下为什么合适；一份 ADR 只记一个决定。

## 4. 流程

1. `new` 建一份“提议中”的 ADR，写背景和备选方案，发给相关人评审；
2. 评审后写决策和后果，状态改成“已采纳”（`status`），`check` 通过；
3. 决定被推翻时，新建一份 ADR 说明新决定，用 `supersede` 标记取代；
4. 定期（比如每季度）看“重新评审条件”是否已经触发。
