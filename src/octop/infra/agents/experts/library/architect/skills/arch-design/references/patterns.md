# 常见架构模式：什么时候用，什么时候别用

每个模式都有代价。先看你有没有它要解决的那个问题。

| 模式 | 解决什么问题 | 适合 | 不适合 / 代价 |
|------|--------------|------|---------------|
| **模块化单体** | 边界清楚、部署简单 | 团队 < 20 人、业务还在变化、没有独立扩展需求 | 模块之间要靠规则约束依赖，否则会烂成一团；整体一起发布 |
| **微服务** | 多个团队独立开发、发布、扩展 | 团队多、业务边界稳定、不同模块扩展需求差别大 | 分布式事务、联调、部署、监控全部变难；人少时是负担 |
| **分层架构** | 职责分开，依赖单向（接口层→业务层→数据层） | 大多数业务系统 | 层多了变成“传话筒”；要避免下层依赖上层 |
| **六边形（端口和适配器）** | 业务逻辑和外部技术解耦，便于测试和替换 | 外部依赖多变、要长期维护的核心业务 | 小项目显得啰嗦 |
| **事件驱动 / 消息队列** | 解耦、削峰、异步处理慢任务 | 下游多、允许延迟、有突发流量 | 要处理重复、乱序、丢失；排查链路变长；要对账 |
| **CQRS（读写分离模型）** | 读和写的模型、规模差别很大 | 读多写少且查询复杂、报表和搜索 | 两套模型、同步延迟；简单 CRUD 不要用 |
| **事件溯源** | 要完整历史、审计、回放 | 金融账务、强审计 | 学习和运维成本高，查询要另建视图；大多数业务不需要 |
| **缓存（旁路缓存）** | 降低读延迟和数据库压力 | 读多写少、数据允许短暂过期 | 失效策略、穿透、雪崩、一致性；先优化查询和索引 |
| **读写分离** | 读压力大于写 | 读多写少 | 主从延迟导致读到旧数据；写后立刻读要走主库 |
| **分库分表** | 单库容量或写入撑不住 | 数据量级上亿且增长快 | 跨分片查询和事务难；先试归档、冷热分离、升级配置 |
| **API 网关 / BFF** | 统一入口、鉴权、限流；按端定制接口 | 多端、多个后端服务 | 成为单点和瓶颈；BFF 太多会重复 |
| **服务网格 / Sidecar** | 统一治理服务间通信 | 服务很多、治理需求复杂 | 复杂度和资源开销高，几个服务时不需要 |
| **Serverless / 函数计算** | 流量波动大、按用量付费 | 偶发任务、事件处理、小型接口 | 冷启动、时长和并发限制、本地调试和厂商绑定 |
| **插件化 / 扩展点** | 让第三方或不同客户扩展功能 | 平台型产品 | 扩展接口一旦发布就难改；要考虑隔离和安全 |
| **多租户** | 一套系统服务多个客户 | SaaS | 数据隔离、资源争用、定制化；决定隔离粒度（库、表、行） |
| **多活 / 异地容灾** | 机房级故障不停服 | 极高可用要求 | 数据同步和冲突、成本翻倍；多数业务用同城双可用区加异地备份就够 |

## 拆服务的判断

拆之前问这些问题，**答案大多是“是”才拆**：

1. 这块业务有独立的团队负责吗？
2. 它的发布节奏或扩展需求和别的模块明显不同吗？
3. 它的数据能独立存放，不需要和别的模块一起事务吗？
4. 它和别的模块的接口稳定吗？
5. 团队有能力运维多一个服务（监控、发布、值班）吗？

只满足“代码太大了”不是拆服务的理由，先做模块化。

## 同步还是异步

| 用同步 | 用异步（消息队列） |
|--------|------------------|
| 调用方要立刻拿到结果才能继续 | 调用方不关心结果或可以稍后查 |
| 流程短，下游稳定 | 下游多、慢、不稳定 |
| 强一致要求 | 允许最终一致 |
| 排查要简单 | 要削峰、要解耦 |

异步的底线：消息要持久化、消费要幂等、失败要有死信和重试、要有监控和对账。

## 数据存储怎么选

| 需求 | 优先考虑 |
|------|----------|
| 业务数据、事务、关联查询 | 关系型数据库（PostgreSQL / MySQL） |
| 缓存、计数、排行榜、分布式锁 | Redis 一类内存存储 |
| 文件、图片、备份 | 对象存储 |
| 全文检索、多条件筛选 | 搜索引擎（Elasticsearch / OpenSearch） |
| 海量时间序列（监控、日志） | 时序库 / 日志系统 |
| 分析报表、大规模聚合 | 列式分析库（ClickHouse 等），不要拿业务库跑 |
| 向量检索（AI 应用） | 向量库，或带向量扩展的关系库（数据量小时先用后者） |

默认一个关系型数据库打天下，遇到具体瓶颈再引入其他存储。每多一种存储，就多一份运维、备份和一致性的负担。
