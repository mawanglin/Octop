# 架构评审

> `scripts/`、`references/` 路径相对于本技能目录。

## 1. 先弄清评审目的

| 目的 | 重点 |
|------|------|
| 接手陌生系统 | 整体结构、核心模块、数据流、谁依赖谁；先出图，再谈问题 |
| 重构或拆分前 | 模块边界、循环依赖、枢纽模块、改动影响面 |
| 性能或稳定性问题 | 瓶颈、单点、同步调用链、容量余量、故障传播 |
| 技术债盘点 | 超大文件、重复、越层调用、缺测试的核心模块，按“影响 × 改动成本”排序 |
| 上线前评审 | 可观测、安全、回滚、容量、依赖 |

## 2. 扫描依赖

```bash
python scripts/arch_scan.py scan 项目目录
python scripts/arch_scan.py scan 项目目录 --depth 2 --exclude dashboard,docs --top 15
python scripts/arch_scan.py scan 项目目录 --layers cli,api,infra,utils        # 内层不能 import 外层
python scripts/arch_scan.py scan 项目目录 --mermaid outputs/arch/deps.md      # 写出 Mermaid 依赖图
python scripts/arch_scan.py scan 项目目录 --json                              # 给程序处理
python scripts/arch_scan.py scan monorepo --root services/order               # 指定源码根
python scripts/arch_scan.py scan 项目目录 --fail-on-cycle                     # 有循环依赖时退出码为 3
```

| 选项 | 作用 |
|------|------|
| `--depth auto\|1\|2\|3` | 组件取前几层目录；默认 auto，挑第一个能分出 5 个以上组件的 |
| `--root` | 源码根；默认有 `src/` 就用它，里面只有一个包目录时自动进入 |
| `--exclude` | 跳过的目录名，逗号分隔（生成物、第三方代码、构建产物） |
| `--layers` | 从外层到内层的组件名；内层 import 外层算违规，组件名可以写前缀（`infra` 覆盖 `infra/db`） |
| `--include-tests` | 把测试文件也算进去（默认不算） |
| `--mermaid` | 把依赖图写到文件；`--max-edges` 控制画多少条边 |

退出码：0 正常，3 有分层违规（或 `--fail-on-cycle` 且有循环依赖），1 输入错误。

**支持的语言**：Python（解析语法树，区分顶层 import、函数内懒加载、`TYPE_CHECKING` 类型引用）和 JS / TS（`import`、`export … from`、`require()`、`import()`，相对路径和 `@/` 别名）。其他语言只统计文件数和行数。

## 3. 读结果

| 输出 | 怎么看 |
|------|--------|
| **组件表** | 文件数、代码行、依赖了几个组件（出）、被几个组件依赖（入）。**不稳定度** = 出 ÷（出 + 入）：接近 0 的被很多组件依赖，改动代价大，应该稳定、抽象；接近 1 的依赖很多别人，容易受影响，通常是上层 |
| **循环依赖（文件级）** | 顶层 import 就成环的文件，是真问题：没法单独理解和测试，有些语言还会在加载时出错。找环里依赖最少的那一条，改成依赖接口，或把共用部分抽出来 |
| **懒加载才成环** | 靠函数内 import 才没出错的环。能跑，但说明依赖方向有问题，要看是不是被迫绕开 |
| **组件间双向依赖** | A 依赖 B、B 也依赖 A。不一定有文件环，但边界没分清：判断哪边是上层，让依赖单向 |
| **分层违规** | 内层 import 了外层（如业务层 import 接口层）。通常是真问题，除非用户的层次定义有误 |
| **枢纽组件** | 出入度都高，改动牵一发动全身；考虑拆分，或者把对外接口收窄 |
| **超大文件** | ≥800 行。看是不是承担了多个职责；不一定要拆，但要有理由 |
| **依赖图** | 实线是顶层 import，虚线是懒加载或仅类型；红色是含文件级环的组件；数字是 import 条数 |

**脚本的局限（必须告诉用户）**

- 只看 import：看不到运行时的调用、反射、依赖注入、消息队列、共享数据库表这些隐形依赖；
- 目录划分不等于真实的模块边界，边界不一致时要用 `--depth` / `--root` 调整；
- 组件内部的零散文件会归到同一个组件，细看要加大 `--depth`；
- 只扫 Python 和 JS / TS；
- 它给的是线索，**每一条都要读代码确认**，不能直接当作结论。

## 4. 对照清单评审

扫描只覆盖代码依赖。完整评审对照 `references/review-checklist.md`：边界与职责、数据、接口、可靠性、性能与容量、安全、可观测、部署与发布、可维护性。问用户要信息，问不到的列入“待确认”。

## 5. 输出格式

```
# <系统名> 架构评审
## 1. 结论（先说）          整体判断，最重要的 3 个问题
## 2. 系统概览              规模、技术栈、组件和依赖图（Mermaid）
## 3. 问题清单              按“影响 × 改动成本”排序，逐条：
                            位置 | 证据（扫描结果、代码行）| 影响 | 建议 | 工作量（小/中/大）
## 4. 做得好的地方          值得保留的设计，避免重构时丢掉
## 5. 建议的行动顺序        先做什么、后做什么、哪些可以不做
## 6. 没有覆盖到的          扫描和评审的局限、需要用户补充的信息
```

## 6. 规则

- 先读代码再下结论：脚本发现的环、违规和超大文件，至少抽查最严重的几处。
- 区分“事实”（扫描结果、代码位置）和“判断”（影响、建议），判断要说明依据。
- 建议要可执行，并写出代价；不推荐团队维护不了的方案；重构建议要有分步、可回滚的路径，不要“推倒重来”。
- 不改用户的代码；只读扫描。
- 评审结果可能涉及业务机密，只在本次工作使用。
