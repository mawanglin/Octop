# 0001. 订单事件用消息队列异步通知下游

- 状态：已采纳
- 日期：2026-11-02
- 决策人：后端负责人、订单组、结算组

## 背景

订单服务在支付成功后，要通知库存、积分、结算、短信四个下游。现在订单服务逐个同步调用它们的接口，平均耗时 380 毫秒，其中积分和短信不影响下单结果，却经常因为超时拖慢支付回调；上个月积分服务重启 6 分钟，期间有 1,200 笔订单的回调超时、重试后重复发放了积分。

约束：团队 6 人，没有专职运维；订单高峰约 300 单/秒；库存必须在回调里同步扣减，不能延后。

## 决策驱动因素

- 下游故障不能拖慢支付回调
- 积分、短信、结算允许几秒内的延迟，不允许丢消息或重复处理造成资金差错
- 运维成本要低，团队没人维护复杂的集群

## 备选方案

### 方案 A：保持同步调用，加超时和重试

- 做法：给每个下游设 500 毫秒超时，失败后在订单服务里重试三次。
- 优点：改动最小，一周内能上线。
- 缺点：下游越多，回调越慢；重试靠订单服务自己，服务重启就丢；重复调用要每个下游自己做幂等。

### 方案 B：RabbitMQ 异步通知

- 做法：支付成功后写一条订单事件到队列，积分、短信、结算各自订阅处理；库存仍同步扣减。
- 优点：下游故障不影响回调；消息可持久化、可重试、有死信队列；团队里有人用过；单机即可承载 300 单/秒。
- 缺点：多一个要运维的组件；要处理重复消息（下游要做幂等）；消息顺序只能在单队列内保证。

### 方案 C：Kafka

- 做法：订单事件写 Kafka 主题，各下游作为消费组消费。
- 优点：吞吐远超需求，消息可回放，以后做数据分析可复用。
- 缺点：集群至少 3 个节点，运维和学习成本明显更高；现阶段的需求用不上回放和高吞吐。

## 决策

采用方案 B：订单事件通过 RabbitMQ 异步通知积分、短信、结算，库存保持同步扣减。

理由：它直接解决“下游故障拖慢回调”的问题，运维成本在团队可承受范围内；方案 A 不能根治，方案 C 的能力远超当前需求，复杂度不值得。

## 后果

### 好处

- 支付回调只依赖库存和写队列，预计耗时降到 100 毫秒以内
- 下游可以独立重启、扩容，故障不再扩散到下单链路
- 失败的消息进入死信队列，可以人工或定时重放

### 代价和风险

- 新增一个有状态组件：需要监控队列堆积、磁盘和连接数，先用云厂商托管版降低运维成本
- 下游必须按订单号做幂等，否则重复消息会重复发积分；上线前每个下游要补幂等测试
- 订单写库和写队列不在一个事务里，可能出现“订单成功但消息没发出”：用本地消息表加定时补发，作为第一版的缓解
- 事件格式一旦被多个下游依赖就很难改，要给事件加版本号

## 重新评审条件

- 峰值超过 3,000 单/秒，或需要把订单事件用于实时分析和回放时，重新评估 Kafka
- 下游超过 8 个，或出现需要严格跨主题顺序的场景
- 托管版 RabbitMQ 连续两个季度出现影响业务的故障
