# 架构设计

> `references/` 路径相对于本技能目录。

## 1. 先问清楚（一次问完）

| 方面 | 要问的 | 为什么 |
|------|--------|--------|
| 业务目标 | 解决什么问题、谁用、成功的标准是什么、不做什么 | 架构服务于业务目标；范围不清，方案没有边界 |
| 规模 | 用户数、日活、数据量、峰值（促销、整点）、一年后的预期 | 决定要不要分布式、要不要缓存和队列 |
| 团队 | 几个人、擅长什么技术、有没有运维、能接受的学习成本 | 团队不会运维的组件，就是风险 |
| 时间和预算 | 什么时候要上线、云成本上限、能不能买托管服务 | 决定自建还是购买、一步到位还是分期 |
| 约束 | 合规（数据出境、等保、行业监管）、必须用的技术、必须对接的系统 | 硬约束先排除不可行方案 |
| 现状 | 有没有老系统、数据怎么迁、能不能停机 | 迁移往往比新建更难 |
| 质量要求 | 可用性目标（几个九）、延迟目标、数据丢失能容忍多少 | 没有目标就没法判断方案够不够 |

用户答不出来的，**列出你采用的假设**并请他确认，不要默默替他决定。

## 2. 质量属性排序

从下面挑出**最重要的 3 个**，并写清楚各自的具体目标（可度量）：

| 属性 | 可度量的写法 | 常见代价 |
|------|--------------|----------|
| 性能 | P99 延迟 < 300 毫秒；峰值 2,000 QPS | 缓存、异步带来一致性和复杂度 |
| 可用性 | 99.9%（每月停机 < 43 分钟）；单机故障自动恢复 | 冗余、多副本，成本和复杂度翻倍 |
| 一致性 | 支付强一致；点赞数允许几秒延迟 | 强一致牺牲可用性和延迟 |
| 安全 | 数据加密、最小权限、审计可追溯 | 开发和运维成本 |
| 可维护 | 新人 1 周能改动；模块可单独测试 | 前期多花时间划边界 |
| 可扩展 | 用户 10 倍增长时只加机器 | 过早设计带来浪费 |
| 成本 | 月云成本 < 2 万元 | 限制选型 |
| 上线速度 | 6 周内上线第一版 | 技术债，后期重构 |

不可能全都要。详细说明和取舍见 `references/quality-attributes.md`。

## 3. 方案对比

每个重要决定至少两个方案，用表格对比，**每个方案都写代价**：

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 满足的质量目标 | | |
| 实现复杂度和工期 | | |
| 团队熟悉程度 | | |
| 运维成本 | | |
| 主要风险 | | |
| 什么情况下会失效 | | |

推荐一个，写明为什么，以及“什么情况下应该换”。常见模式的适用和不适用见 `references/patterns.md`。

**默认倾向（没有强理由时）**

- 从模块化的单体开始，边界清楚，以后需要时再拆；
- 一个主数据库；缓存、消息队列、搜索引擎在遇到具体问题时再加；
- 优先托管服务（数据库、对象存储、消息队列、认证）；
- 同步调用优先，需要解耦、削峰或慢任务时再异步；
- 每个新增的组件都要问一句：谁运维？坏了怎么办？

## 4. 画图（Mermaid）

按 C4 分层，从粗到细，读者想看多细画多细：

| 层 | 回答的问题 | 画什么 |
|----|-----------|--------|
| 系统上下文 | 这个系统和谁交互 | 用户、本系统（一个框）、外部系统 |
| 容器 | 系统由哪些可部署单元组成 | 应用、数据库、队列、缓存，以及它们之间的协议 |
| 组件 | 某个容器内部怎么分模块 | 模块和依赖方向 |
| 时序 | 一个关键流程怎么走 | 参与者、消息、成功和失败分支 |
| 部署 | 跑在哪里 | 机房/可用区、集群、网络边界 |

模板和画法要点见 `references/diagram-templates.md`。画图原则：一张图一个主题；框里写名称和职责，线上写协议和方向；超过 15 个框就拆图；图和代码不一致时，以代码为准并更新图。

## 5. 分阶段演进

大方案要拆成可交付的阶段，每个阶段都能独立上线、能回滚：

1. **第一版**：最小可用，验证需求；明确这一版故意不做什么；
2. **加固**：监控、告警、备份、压测、安全加固；
3. **扩展**：在真实瓶颈出现后针对性优化（读写分离、缓存、拆服务）。

每个阶段写：目标、范围、验收标准、风险、回滚办法。

## 6. 方案文档模板

```
# <系统/模块> 架构方案
## 1. 背景和目标        要解决什么问题，成功标准，不做什么
## 2. 约束和假设        团队、时间、预算、合规；本方案采用的假设（标明待确认的）
## 3. 质量目标          最重要的 3 个质量属性及可度量目标
## 4. 容量估算          用户、QPS、存储、带宽、节点数（capacity.py，列出假设）
## 5. 方案对比          备选方案表和推荐理由
## 6. 架构图            系统上下文、容器、关键流程时序
## 7. 关键设计          数据模型、接口、一致性、安全、可观测、部署
## 8. 风险和缓解        技术风险、依赖风险、人员风险
## 9. 分阶段计划        各阶段目标、验收、回滚
## 10. 待确认问题       需要用户或团队决定的事项
```

重要决定同时用技能 `adr-writer` 写成 ADR。

## 7. 交付时要说明

- 采用了哪些假设，哪些需要用户确认；
- 推荐方案的代价和失效条件；
- 估算只是量级，上线前需要压测验证；
- 没有覆盖的方面（比如合规细节、具体云产品的限额）要请相关负责人确认。
