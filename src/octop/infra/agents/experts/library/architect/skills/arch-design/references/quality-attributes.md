# 质量属性：怎么定目标、怎么取舍

## 1. 可用性

| 目标 | 每月允许停机 | 通常需要 |
|------|--------------|----------|
| 99% | 7.2 小时 | 单机加备份，出事人工恢复 |
| 99.9% | 43 分钟 | 应用多副本 + 数据库主从自动切换 + 监控告警 |
| 99.95% | 22 分钟 | 上述加灰度发布、快速回滚、容量余量 |
| 99.99% | 4.3 分钟 | 多可用区、自动故障转移、完善的演练；成本和复杂度明显上升 |
| 99.999% | 26 秒 | 多地域主动容灾，绝大多数业务不需要 |

- 整体可用性是各部件**串联相乘**，再看冗余部分**并联**（`capacity.py compose`）：五个 99.9% 的部件串联只有约 99.5%。
- 先定义“什么算不可用”（哪些接口、多高的错误率、多长的响应时间），再谈几个九。
- 提高可用性的顺序：去掉单点 → 自动恢复 → 灰度和快速回滚 → 多可用区。多数故障来自**变更**，不是硬件。

## 2. 性能

- 指标要写分位数（P50 / P95 / P99），不要只看平均值；说明在什么并发和数据量下。
- 先找瓶颈再优化：数据库（慢查询、索引、锁）占大多数，其次是外部调用和序列化。
- 手段按代价从低到高：索引和查询优化 → 缓存 → 读写分离 → 异步化 → 分库分表。每一步都带来一致性或运维的代价。
- 缓存要回答：缓存什么、多久失效、更新时怎么保证不读到旧数据、缓存挂了数据库扛得住吗。

## 3. 一致性

| 需求 | 做法 | 代价 |
|------|------|------|
| 强一致（钱、库存扣减） | 单库事务；或把相关数据放进同一个服务和数据库 | 难以水平扩展 |
| 最终一致（积分、通知、统计） | 消息队列 + 幂等消费 + 补偿 | 要处理重复、乱序、延迟，要有对账 |
| 跨服务事务 | 尽量避免（调整服务边界）；必须时用本地消息表、Saga | 复杂，要写补偿逻辑 |

经验：如果两个服务总是要在一个事务里改数据，它们大概率不该拆开。

## 4. 安全

- 认证（你是谁）和授权（你能做什么）分开设计；授权在服务端检查，不信任前端。
- 最小权限：服务账号、数据库账号、云角色只给需要的权限。
- 数据分级：个人信息、凭证、支付信息单独存放、加密、限制访问、留审计日志。
- 机密不进代码和镜像，用密钥管理服务。
- 外部输入全部校验；对外接口限流；依赖定期扫描漏洞。

## 5. 可维护性

- 模块边界清楚、依赖方向一致（单向），能单独测试和理解（`arch_scan.py` 可以检查循环依赖和越层调用）。
- 可观测：日志、指标、链路追踪三件套；每个请求有 ID 贯穿；告警指向可执行的动作。
- 配置和环境一致，部署可重复，回滚有演练。
- 文档：架构图 + 决策记录 + 运行手册，写给半年后接手的人。

## 6. 可扩展性

- 先垂直扩展（加配置）和无状态水平扩展（加副本），最后才是分片。
- 有状态的东西（数据库、会话、文件）是扩展的难点：会话放缓存、文件放对象存储、数据库按需读写分离。
- 不要为“10 倍增长”提前设计分片；设计时留出**能迁移的余地**（主键不依赖单库自增、业务不跨租户查询）。

## 7. 成本

- 把成本当作需求写进目标：每月预算、单用户成本。
- 大头通常是计算、存储、流量、第三方 API；先量化再优化。
- 托管服务单价高，但省人力；自建便宜，但要算上运维的人天。

## 8. 常见取舍

| 想要 | 往往要放弃 |
|------|-----------|
| 更高可用性 | 更低成本、更简单 |
| 更强一致 | 更高延迟、更低可用性 |
| 更快上线 | 更干净的设计（要记下技术债并安排偿还） |
| 更灵活可扩展 | 更简单易懂 |
| 更多自研控制 | 更少运维人力和更快迭代 |
