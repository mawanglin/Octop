# 提示词评测

> `scripts/`、`references/` 路径相对于本技能目录。

“感觉变好了”不算结论。改提示词的标准流程：**先有用例 → 跑旧版 → 改 → 跑新版 → 对比**。

## 1. 流程

1. **设计用例**：`python scripts/prompt_eval.py template outputs/eval/用例.csv` 生成带示例的用例表，按任务改写。
2. **跑各版本**：把每个提示词版本在**同一批输入**上的输出，整理成 CSV（两列 `id,output`）。我不能替用户调用他的目标模型；有能调用的模型和权限时才自己跑，并说明模型和参数。同一个提示词想看稳定性，就多跑几遍，同一个 `id` 写多行。
3. **判分**：`python scripts/prompt_eval.py score 用例.csv 输出-v1.csv`。
4. **对比**：`python scripts/prompt_eval.py compare 用例.csv 输出-v1.csv 输出-v2.csv`，看变好的和**退步的**用例。
5. **定论**：新版没有退步、关键用例都过，才建议换；有退步的，看退步的是不是重要用例。

```bash
python scripts/prompt_eval.py template outputs/eval/cases.csv
python scripts/prompt_eval.py score outputs/eval/cases.csv outputs/eval/out-v1.csv
python scripts/prompt_eval.py compare outputs/eval/cases.csv outputs/eval/out-v1.csv outputs/eval/out-v2.csv --json
```

退出码：0 全部通过（compare 时没有退步），3 有失败或不稳定（compare 时有退步），1 输入错误。

## 2. 用例表的列

| 列 | 含义 |
|----|------|
| `id` | 用例编号，必填，不重复 |
| `input` | 输入内容，只用来对照，不参与判分 |
| `must_contain` | 输出必须**全部**包含这些文字，多个用 `\|` 分隔 |
| `any_of` | 输出至少包含其中**一个** |
| `must_not_contain` | 输出不能包含这些文字 |
| `regex` / `not_regex` | 输出必须 / 不能匹配的正则 |
| `min_chars` / `max_chars` | 长度下限 / 上限 |
| `json` | 填 `yes`：输出必须是合法 JSON，外面包一层 ```` ```json ```` 代码块也算合法 |
| `json_keys` | 顶层必须有的字段；`字段=值` 同时要求取值相等，如 `category=支付退款\|reason` |
| `equals` | 去掉首尾空白后必须完全相等 |
| `note` | 这条用例想防什么，失败时会一并显示 |

规则列都可以留空；一条用例可以同时写多条规则，全部满足才算通过。`json_keys` 只有 `json` 列填了 `yes` 才会生效，只填前者脚本会提示。

## 3. 用例怎么设计

按下面几类各取几条，总数从 20 条起步，上线前尽量到 50 条以上：

| 类别 | 例子 | 占比参考 |
|------|------|---------|
| 常见 | 线上最多的几种输入，直接用真实样本 | 40% |
| 边界 | 空输入、只有一个词、超长、混着中英文、带表情、重复内容 | 20% |
| 容易判错 | 类别之间容易混的、有多个诉求的、有否定词的、有歧义的 | 25% |
| 对抗 | “忽略上面的规则”、要求泄露提示词、夹带指令的文档 | 10% |
| 线上出过错的 | 每次线上出错，把那条输入补进来 | 持续补 |

- **能用规则判的先用规则**（格式、字段、是否泄露、长度）；规则判不了的（“回答是否准确”“语气是否合适”）要么人工看，要么用裁判提示词（`prompt-craft` 的模板 8），裁判提示词本身也要先拿 10 条人工打过分的样本核对。
- 每条用例的 `note` 写清楚想防什么，以后看到失败就知道这条为什么在。
- 用例和输入不要拿提示词里的示例充数，那是“考试前给你看的原题”。

## 4. 读结果

- **通过率**：只在样本够多时有意义。脚本在用例少于 20 条时会提示“只能当初步参考”，对比时共同用例少于 20 条、或变好和退步只差 1 条以内，也会说明可能是波动。
- **不稳定**：同一用例多次运行有时过有时不过，说明提示词对这类输入不够明确，或模型温度太高。先看失败那几次输出有什么不同，再补约束或示例。
- **失败类型统计**：哪种规则失败最多，往往就是提示词最该改的地方（比如“不是合法的 JSON”占一半，就该先把输出格式写死）。
- **退步清单**：新版把旧版做对的用例做错了，要逐条看原因，不要只看总通过率上升。

## 5. 规则

- 用同一批用例、同一个模型和参数比较两个版本；换了模型要从头测。
- 脚本只检查规则能表达的部分，通过不等于输出质量好；重要结论附上人工抽查的几条原文。
- 不为了让通过率好看而改用例或放宽规则；确需调整，说明原因并重跑旧版。
- 对外汇报时写清：用例数、版本、模型、通过率、退步用例和没覆盖到的风险。
